Direct checked lookup improves the issue’s million-call Rust workload by 1.34–1.67x
across two cohorts; checked caching improves it by 1.71–1.95x. These are gains beyond
PR #2483, with debug:false selected at instantiation. A generation-counted cache
measures 1.73x in the follow-up, but only 1.02x versus the simpler checked cache
(95% paired bootstrap interval 0.87–1.11): no additional benefit established.

A native Wasm accessor module backed by two mutable globals improves the same
workload by 7.37–10.10x and reaches 1.28–1.45x the WASIp2 time. It uses the original
guest core Wasm bytes: replacing JS imports with native Wasm exports removes the
Wasm-to-JS transition. This prototype lacks task/thread save and restore and fails
thread-isolation checks; its result is a single-task lower bound.

Interpretation and implementation priorities:

1. Start with direct checked lookup. Read the task register without snapshotting
   it, resolve the live thread without allocating an AsyncThreadMeta wrapper,
   and avoid redundant task()/id() calls. Keep component selection, task-ID
   validation, executing-task fallback, slot checks, and i32 validation. Restrict
   removal of register copies to this hot path; other callers use snapshots.

2. Prototype a cache at the execution-context boundary. The checked cache here
   attaches thread/table references to task-register objects and still checks
   table membership and task ID on each hit. It avoids the component Map lookup.
   A production cache needs an explicit ownership/lifetime contract and audits
   of register snapshots, table replacement, stale post-return metadata, and
   retained thread references. The epoch prototype validates a generation and
   thread/component/task IDs instead of reading the table, but does not establish
   an extra performance gain. Its generation increments on insert/remove/clear.

3. Erase debug-only argument construction when debug is disabled, including
   RepTable#get, rather than just substituting an empty logger. Logging removal
   alone is inconclusive on the full Rust workload. Combining context-log removal
   with elimination of metadata copies gives 1.44x [1.11, 1.89]. Removing all
   embedded diagnostics does not establish an additional gain over direct lookup.
   Production integration must retain debug-enabled behavior.

4. Explore a tiny native Wasm getter/setter module as the route toward WASIp2
   performance. It avoids guest binary rewriting. Schedule-aware save/restore
   must handle JSPI suspension/resumption, nested component calls, both context
   slots, realloc, destructors, and fused-adapter/post-return context. Measure
   the cost at task-switch boundaries before treating the lower bound as an
   achievable general speedup. A plain global array or unchecked cache fails
   isolation and should not be adopted as an optimization.

Validation and scope:

- Nine generated variants (including the baseline) pass focused tests covering
  both slots, nested/restored thread registers, component selection, dead-thread
  fallback, recycled IDs, independent stores, invalid arguments, and table clear.
- The unchecked cache, single array, and Wasm globals each fail the expected
  isolation test. They are diagnostic lower bounds.
- 143 primary Rust processes, 66 follow-up Rust processes, and 77 warmed
  microbenchmark processes completed with checked results. Internal repeated
  microbenchmark samples are not counted as independent processes.
- The saved native driver builds with its pinned Cargo.lock and reproduces the
  baseline JavaScript and every core Wasm module byte for byte. The baseline JS
  SHA-256 is 203f84b3dc50dc577f96c7977fad46215160b5924b7cb53e5d3322fe216ca45b.
- Rust formatting, JavaScript formatting/lint, and whitespace checks pass.
- These are generated-output experiments. Real JSPI interleavings and the full
  transpiler/runtime integration suite have not been validated for these patches.
  The larger shell-interpreter workload was not available; no end-to-end shell
  or I/O throughput gain is claimed.
