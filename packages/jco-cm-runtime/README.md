# `@bytecodealliance/jco-cm-runtime`

An optional Component Model runtime for JavaScript generated by Jco. Its
operations implement the [Canonical ABI](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md).
The experimental JavaScript runtime API is versioned independently of the npm package.

```sh
npm install @bytecodealliance/jco-cm-runtime
jco transpile component.wasm --cm-runtime-es-module @bytecodealliance/jco-cm-runtime
```

Without the option, intrinsics remain inline. Neither `jco` nor `jco-transpile`
needs a concrete runtime installed to transpile. Resolution happens when the
bindings are loaded or bundled.

## API version 2: named modules and specific contexts

`cmRuntimeEsModule` identifies a **package or directory base**. Generated bindings
statically import `CM_RUNTIME_API_VERSION` from the `runtime` subpath and
resource operations and storage initializers from `intrinsics/resource`, selected conversions from
`intrinsics/conversion`, JavaScript helpers from `intrinsics/js-helper` and
string operations/codecs from `intrinsics/string` and the global WebIDL adapter
from `intrinsics/webidl`, with core operations, constructors and state owners
from `intrinsics/core`, component state/scheduling from `intrinsics/component`,
and waitable constructors/operations from `intrinsics/waitable`.
Only implemented subpaths are published.
Root exports the same metadata and types as `runtime`; there is no root factory.

| Base                               | Resource import                                        | Version import                             |
| ---------------------------------- | ------------------------------------------------------ | ------------------------------------------ |
| `@bytecodealliance/jco-cm-runtime` | `@bytecodealliance/jco-cm-runtime/intrinsics/resource` | `@bytecodealliance/jco-cm-runtime/runtime` |
| `custom-runtime`                   | `custom-runtime/intrinsics/resource`                   | `custom-runtime/runtime`                   |
| `./runtime/`                       | `./runtime/intrinsics/resource.js`                     | `./runtime/runtime.js`                     |
| `file:///path/dist/`               | `file:///path/dist/intrinsics/resource.js`             | `file:///path/dist/runtime.js`             |
| `https://example.test/runtime/`    | `https://example.test/runtime/intrinsics/resource.js`  | `https://example.test/runtime/runtime.js`  |

One optional trailing slash is normalized. Relative bases resolve from the
**generated bindings**, not the transpilation process's working directory.
Directory/URL bases use real `.js` files. Use file URLs for Windows paths.
Control characters, empty bases, unsupported URL schemes and query/fragment
suffixes on directory bases are rejected. Bare packages named `something.js`
are packages; relative/URL file bases such as `./provider.js` must migrate to a
directory. Browser package imports need normal import-map or bundler setup;
map each public subpath to its `.js` file. HTTP servers must serve the whole
runtime directory tree with JavaScript MIME types.

Bindings check version 2 before use. Missing subpaths or named exports fail
through the native ES module loader. The current externalized set is all 16 resource variants, the shared handle-table
and scope owners, all 19 conversion operations, both JavaScript helpers, all ten
string variants, the WebIDL proxy and the remaining 52 core variants
(126/274 logical intrinsic variants, including all 16 component and eight waitable variants);
other families remain inline during migration.

```js
import { tableGet } from '@bytecodealliance/jco-cm-runtime/intrinsics/resource';

const context = { RuntimeError: WebAssembly.RuntimeError };
const entry = tableGet(context, [1 << 30, 0, 7, 42 | (1 << 30)], 1);
// { rep: 42, scope: 7, own: true }
```

Generated bindings create one stable `ResourceTableGetContext` after selecting
their WebAssembly implementation: once per explicit `instantiate` call, or once
per direct module evaluation. It contains only `RuntimeError`. Tables and handles
are operands; tables remain shared with other operations in that store.
The function has no receiver dependency. It must use the supplied constructor for
traps, including when the global WebAssembly implementation is absent or differs.
No codecs, scratch arrays, scheduler or optional JSPI facilities are initialized
by this operation or by importing runtime metadata.

## Implementing an alternative runtime

`dist/runtime.d.ts`, published at `@bytecodealliance/jco-cm-runtime/runtime`, is
the explicit, self-contained structural contract. It has no imports from default
implementation modules. A TypeScript provider can check its module namespace:

```ts
import type { ResourceModule } from '@bytecodealliance/jco-cm-runtime/runtime';
import * as resource from './intrinsics/resource.js';

const conformance: ResourceModule = resource;
```

Export `CM_RUNTIME_API_VERSION = 2` from your `runtime.js`. Expose `./runtime`
and the implemented `./intrinsics/resource`, `./intrinsics/conversion` and
`./intrinsics/js-helper`, `./intrinsics/string`, `./intrinsics/webidl` and
`./intrinsics/core` and `./intrinsics/component` subpaths
in your package's `exports` map, with their matching
JavaScript and declaration targets. `RuntimeModuleContracts` is a type-only map
of public suffixes to their interfaces; no assembled runtime object is required.
Function-property signatures support strict parameter checking. Type-only
consumption produces no runtime imports.

Structural conformance does not prove package resolution, exact JavaScript arity,
or Canonical ABI behavior. TypeScript permits implementations to ignore arguments.
Test the installed package and its behavior, especially traps and shared state.
Providers may re-export selected default functions. Those functions retain their
own statically imported dependencies: overriding a sibling export does not
intercept its calls. There is no mutable namespace receiver or implicit override
registry. Context-free operations take no dummy context argument.

### Resource table contract

`tableGet(context, table, handle)` reads an array-like table without changing it
and returns `{ rep, scope, own }`.

- Slots 0 and 1 form a sentinel; resource handles start at 1. Indices are shared
  by all handle kinds of a component instance, so a table may contain holes.
- Slot `handle << 1` holds the scope; bit 30 marks a freed entry.
- Slot `(handle << 1) + 1` holds the representation, with bit 30 marking ownership.
  Clear that bit to obtain `rep`; a freed entry stores zero.
- A missing slot, zero representation or freed entry traps with
  `unknown handle index <handle>` using `context.RuntimeError`.

`initializeHandleIndexSpaces()` returns the shared allocator map; resource tables,
waitables and error contexts of a component use the same index space. Table
creation takes that map directly. Removal receives only `RuntimeError`,
`indexSpaces` and `scopeTasks`; transfer additionally selects the actual table
owner. `initializeHandleTables()` and `initializeResourceScopeTasks()` return
collections, with no operation table. Scope initializers return mutable
`{ value }` cells; call/current borrow initializers return `{ borrows }` owners.
Generated code reads and replaces their members directly, so operations observe
the live values rather than captured snapshots. Every selected owner is created
once per instantiation; importing the module creates no map or task.

Borrow transfer receives the actual task registers and a lazy task lookup while
tasks remain inline. Destructors receive only lazy `createTask` and the actual
`registers` owner. Each
destructor creates a synchronous task with fresh context slots and restores the
enclosing task after success or failure. Explicit disposal releases the handle
before invoking a destructor and becomes a no-op on repeated disposal.
`tableEnsureBorrowDrop` and `tableFlag` are context-free.

Changes to the encoding or operation contracts require a new runtime API version.

## Migrating from API version 1

Replace the root `runtime.create(options).intrinsics.resource.tableGet` factory
with a named `tableGet(context, table, handle)` export at `intrinsics/resource`.
Replace provider file specifiers with package/directory bases, publish version 2
at `runtime`, and use the supplied trap capability instead of `this` or ambient
WebAssembly. The v1 provider/factory types and bootstrap are removed. Existing
resource data types remain exported at root and `runtime`. Generated v1 bindings
need to be regenerated for API-v2 runtimes; there is no dynamic legacy fallback.

## Conversion contract

Conversion functions are named exports at `intrinsics/conversion` and satisfy
`ConversionModule`. The eight integer coercions take `StrictNumericContext`
(`{ strict: boolean }`) followed by the value. Context-free character, string,
JSON/result-string, numeric validation and i64 split/merge helpers take operands
only. Strict 32-bit validation precedes coercion; 64-bit conversions first apply
`BigInt`, then validate the converted range. Historical `i32ToChar` fromCharCode
and signed-low-word `mergeInt64` behavior are preserved.

`initializeBitcast32()` returns aliased mutable i32/f32 views;
`initializeBitcast64()` returns aliased i64/f64 views. They return storage, with no
operation table. Generated bindings call only selected initializers, once per
instantiation, and pass the same capability to both conversion directions.
Different instantiations never share scratch storage. Assignment/read sequencing
preserves reentrant coercion. Importing scalar helpers allocates no scratch arrays,
codecs or scheduler state.

```js
import { initializeBitcast32, i32ToF32, toUint32 } from '@bytecodealliance/jco-cm-runtime/intrinsics/conversion';

const scratch = initializeBitcast32();
const one = i32ToF32(scratch, 0x3f800000);
const wrapped = toUint32({ strict: false }, -1);
```

Custom runtimes implementing earlier v2 resource-only output must publish the new
conversion subpath when adopting this compiler. They may re-export defaults or
supply matching named operations with the documented structural capabilities.
A selected override of `requireValidNumericPrimitive` does not intercept default
`toUint32`'s own static dependency; interception must be explicit in an overriding
`toUint32` implementation.

## JavaScript helper contract

`intrinsics/js-helper` satisfies `JsHelperModule`. `emptyFunc(...args)` is a
context-free no-op. `initializeDataViewCache()` creates a `DataViewCacheContext`
containing only a mutable `view`. `dataView(context, memory)` returns that view
when its buffer matches `memory.buffer`, or replaces it with a new view. Generated
bindings create this cache only when a memory load or store selects `dataView`,
once per instantiation. Memory growth and switches between memories refresh the
same live cache owner; independent instantiations have independent caches.

Importing either function allocates no cache. Providers implementing earlier v2
output must add this named subpath when adopting this compiler. A provider may
wrap `dataView` while re-exporting the other defaults; each default uses its own
static implementation dependencies.

## String contract

`intrinsics/string` satisfies `StringModule`. Codec values are created by separate
`initializeUtf8Decoder()`, `initializeUtf16Decoder()` and `initializeUtf8Encoder()`
exports. Generated bindings initialize only selected codecs, once per relevant
instantiation, and preserve the returned object for all method callers. The
structural `StringDecoder`, `StringEncoder` and `StringEncodeInto` interfaces
require only their public methods. Calls preserve the codec's method receiver;
codecs from separate instantiations have independent identity and streaming state.
Decoders use fatal decoding and preserve a leading BOM.

`utf8Encode(encoder, value, realloc, memory)` and its async counterpart receive
the actual selected encoder, shared with direct transcoding method calls. This
explicit capability lets a custom encoder intercept default allocation operations.
Re-exporting a default operation does not intercept its internal static helpers.
`utf16Encode(context, value, realloc, memory)` and its async counterpart receive
only `{ littleEndian: boolean }` from `initializeUtf16Encoding()`, with no codecs.
All encoders use exact allocations, replace unpaired host surrogates and obtain
the memory buffer after realloc returns or resolves. Empty UTF-8 input keeps its
`{ ptr: 1, len: 0 }` sentinel without allocating.

`utf16ValidatingCopy`, `validateGuestChar` and `validateHostChar` are context-free.
Importing this subpath creates no codecs or scratch state. Custom API-v2 runtimes
must publish the new named string subpath when adopting this compiler; they may
re-export defaults or implement the self-contained structural contracts.

## WebIDL contract

`intrinsics/webidl` satisfies `WebIdlModule`.
`initializeWebIdlProxyCache()` returns only `{ proxy: undefined }`;
`globalThisIdlProxy(context)` lazily creates and caches the adapter over the host's
`globalThis`. Importing the subpath or creating the empty cache constructs no
proxy or symbols. Each selected cache owns its adapter and private symbols.

Generated direct-module bindings initialize this context before WebIDL import
destructuring invokes the adapter. Explicit `instantiate` calls use their supplied
imports and select no WebIDL cache. Accessor/setter conventions, HTML/DOM name
normalization, method receivers, proxy argument unwrapping and reflection retain
inline behavior. Native methods that require a receiver still fail when
destructured and called without it. Available properties depend on the host's Web
APIs. Custom API-v2 runtimes must publish this new subpath when adopting this
compiler's direct WebIDL output; they may re-export the matching defaults.

## Core contract

`intrinsics/core` satisfies `CoreModule`. Pure helpers receive operands only.
Compilation receives the selected WebAssembly methods and the applicable Node
policy; the methods keep their original receiver. File compilation creates its
cache only when selected and loads Node filesystem support only when called.
Optional JSPI constructors are read when their operation needs them.

`initializeTaskRegisters()` returns the actual mutable owner shared by task,
component and resource operations. Metadata operations take that owner explicitly.
Synchronous scopes restore both enclosing registers on success or failure;
asynchronous scopes clear their own registers without clearing a different task.
`initializeComponentMemoryMap()` returns the actual shared memory lookup map.
These initializers return state rather than an operation registry.

Constructor initializers return selected class values once per instantiation.
`initializeRepTableClass({ RuntimeError })` preserves `new`, `instanceof` and its
per-class `FREE` sentinel. `initializeComponentErrorClass()` preserves each
store's error constructor and payload behavior. Managed-buffer and manager class
initializers receive only their resource owners or selected buffer constructor.
Separate instantiations have separate class identities; constructors are never
hoisted into shared module state. Importing this subpath initializes no classes,
maps, symbols, codecs or optional platform facilities.

`initializeHasOwnProperty()` returns the native unbound function selected for
the instantiation. Error extraction receives it explicitly and preserves its
`.call` receiver. Default operations use their own static dependencies; overriding
a sibling task operation does not intercept default resource destructor internals.
The explicit host `instantiateCore` callback retains its existing two-argument
signature and takes precedence over the default named core operation.

Custom providers adopting this compiler must publish the core subpath and update
resource borrow/destructor contexts to receive `registers`; the earlier v2
`getCurrentTask`/`withTask` bridge shapes are replaced by shared state and the
remaining narrowly named task capability.

## Component contract

`intrinsics/component` satisfies `ComponentModule`. Separate selected initializers
return the actual instance-flag Map, store-trap error cell, store scheduling owner
and component async-state Map. Trap-message initialization receives only the
compiler's message record. Generated bindings share these owners with inline
tasks and waitables; no universal options object or operation registry is needed.

`checkMayLeave` and its receiver-preserving guard need only instance flags and the
selected trap constructor. Trap normalization receives that constructor and the
actual message lookup. Deadlock checking uses the shared trap, scheduling and
async-state owners; host-operation tracking also receives the selected disposal
symbol. It preserves synchronous results, counts pending asynchronous wake sources
and forwards disposal with the host value's receiver.

`initializeComponentAsyncStateClass(context)` returns a per-instantiation class,
with its own statics and identity. It receives the selected representation-table
constructor, shared handle allocator and flag/trap owners, narrow normalization
and deadlock contexts, and the actual selected `Waitable` constructor. State
lookup receives the selected class and actual state Map. Handles
share the component allocator with resources; subtasks keep their own table.
The class preserves FIFO lock handoff and admission, one resumption per tick,
backpressure accounting and trap interruption. Backpressure waiters resolve only
at zero, once each, including under reentrant handlers; both inline and named
implementations use the same corrected event-driven algorithm.

Core suspending-import contexts now receive `mayLeave`, `traps` and `states`
component contexts. Only their remaining task capabilities are lazy bridges.
Custom providers adopting this compiler must publish the component subpath and
replace the earlier core `checkMayLeave`, `recordTrap` and `throwIfInterrupted`
callbacks with these actual contexts. Defaults use their own static operation
dependencies; overriding a sibling export does not implicitly intercept them.
Importing the module creates no state, timers, classes or waitables.

## Waitable contract

`intrinsics/waitable` satisfies `WaitableModule`. `initializeWaitableClass()`
takes no context and returns a fresh constructor for the instantiation.
`initializeWaitableSetClass(events)` captures only the selected live
`TASK_CANCELLED` code. Component state receives the same selected waitable
constructor, preserving class identity across tasks, component handles and
`instanceof` checks without a factory callback or constructor dependency cycle.

New-set operations receive the actual component lookup and selected set
constructor. Wait/poll also receive the selected trap constructor, a narrow
task lookup and host event-writer capability; poll alone receives `NONE`.
Drop needs lookup, task metadata and the trap constructor. Join needs lookup
and the trap constructor. Removal needs only the trap constructor and its
per-call state/handle operand. Memory and canonical options remain per-call
operands rather than shared runtime state.

Task lookup and event writing remain lazy while those families are inline.
Lookup preserves the generated helper's current-task fallback behavior. Waits
retain their synchronous fast path, cancellation rules, waiter counts and live
memory buffer; pending events are consumed once. Default operations call their
own static dependencies, so overriding a sibling export does not intercept
those calls. Required customization uses the explicit selected capabilities.

Custom providers must publish the waitable subpath and replace the component
constructor's earlier `createWaitable` callback with `Waitable`. Importing the
subpath allocates no store state and reads no optional platform facilities.
