# `@bytecodealliance/jco-cm-runtime`

An optional Component Model runtime for JavaScript generated by Jco's
`js-component-bindgen`.

The JavaScript Component Model runtime API maps closely to the Component Model's
[Canonical ABI](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md),
exposing runtime operations through JavaScript objects and methods. Its
resource operations follow the Canonical ABI's handle, ownership, and trapping
semantics.

Generated modules import a runtime provider, create one runtime instance per
Component Model store, and call reusable operations through its typed
`intrinsics` object. Alternative packages can implement the exported
`ComponentModelRuntimeProvider` interface and be selected with Jco's
`cmRuntimeEsModule` transpilation option. Without that option, Jco emits its
built-in runtime code. Neither `jco` nor `jco-transpile` needs this package
installed to build or transpile components. To use this package, install it in
the generated component's environment and pass its module name as
`cmRuntimeEsModule` (or `--cm-runtime-es-module` with the Jco CLI).

```sh
npm install @bytecodealliance/jco-cm-runtime
jco transpile component.wasm --cm-runtime-es-module @bytecodealliance/jco-cm-runtime
```

The module name is written into the generated bindings and resolved when those
bindings are loaded. The runtime package can be released independently of Jco.

The package's `runtime` export provides the default implementation. Alternative
providers can import it under a local name, delegate unchanged operations to
`create(options)`, and replace selected methods:

```js
import { runtime as defaultRuntime } from '@bytecodealliance/jco-cm-runtime';

export const runtime = {
    apiVersion: defaultRuntime.apiVersion,
    create(options) {
        const instance = defaultRuntime.create(options);
        return {
            ...instance,
            intrinsics: {
                ...instance.intrinsics,
                resource: {
                    ...instance.intrinsics.resource,
                    tableGet(table, handle) {
                        return instance.intrinsics.resource.tableGet(table, handle);
                    },
                },
            },
        };
    },
};
```

This package is currently experimental. Its JavaScript Component Model runtime
API is versioned independently from the npm package version.

## JavaScript Component Model runtime API version 1

The selected module exports a `runtime` object with `apiVersion: 1` and a
synchronous `create(options)` method. The method returns a runtime instance
with `apiVersion: 1`, `intrinsics.core`, `intrinsics.component`, `intrinsics.resource`, `intrinsics.conversion`,
`intrinsics.waitable`, `intrinsics.jsHelper`, `intrinsics.string`, and `intrinsics.webidl`.
Generated bindings pass `requestedApiVersion: 1` to `create`, check both API
versions, and verify the required intrinsic methods. Other runtime intrinsics
continue to be generated inline.

Generated bindings pass the selected WebAssembly implementation in
`options.platform.WebAssembly`, including any per-instantiation override.
Providers must use its `RuntimeError` constructor for resource traps so that
the bindings can identify the trap and reject subsequent calls to the trapped
component. When this package's `runtime.create` is called directly without a
platform override, it uses the global WebAssembly implementation.

Intrinsic methods are bound to their namespace object. Constructors, symbols,
constants, and shared state retain their original values. In particular,
constructors support `new`, `instanceof`, and static members; `hasOwnProperty`
retains its `.call` receiver. Codec objects are kept as objects, with their
required methods checked during instantiation. A
`resource.tableGet` implementation may use `this` to access per-store state.
Each call to the generated `instantiate` function creates a fresh runtime;
direct ES module output creates its runtime when the module is evaluated.
Generated bindings currently do not invoke the optional `dispose()` hook, so
providers must not rely on it for automatic cleanup.

### Core helpers

`intrinsics.core` implements the shared helpers from bindgen's `intrinsics/mod.rs`:
errors, validation, symbols, compilation, memory registration, representation
tables, managed buffers, task registers, and conditional suspension. `CoreIntrinsics`
describes the methods and values. Handle tables and the resource scope counter
remain in `intrinsics.resource.state`, shared with managed buffer transfers.

Each runtime owns its `RepTable`, `ManagedBuffer`, and `BufferManager` classes,
default `bufferManager`, memory map, task registers, and conditional-suspension
module registry. `RepTable` can use a component's shared `HandleIndexSpace`;
clearing a table resets its size and releases its live indices. Managed buffers
use the generated element lift/lower callbacks described by `BufferElementMetadata`
and `BufferElementContext`, including resource ownership transfers.

Compilation and instantiation helpers use `options.platform.WebAssembly`.
`compile`, `compileStreaming`, `instantiate`, `Instance`, and `Suspending` are
only required when an operation uses them. Runtime creation does not compile
Wasm or require JSPI. Generated bindings continue to load conditional-suspension
modules, including through `getCoreModule` in precompiled mode, into
`core.conditionalSuspendingWasm`. Instantiated output preserves the caller's
`instantiateCore` callback. Compiler-owned FACT trap discriminants and messages
arrive through `options.factTrapMessages`.

`currentTaskMeta` is the shared task register. Synchronous task scopes restore
the enclosing registers; asynchronous scopes clear the completing task while
preserving another component's active task. During migration, suspending imports
use lazy `options.coreContext` callbacks to consult the generated module's
component and task helpers. Component helpers now use the external runtime;
task helpers remain inline. Providers must defer these callbacks until an import runs,
after generated task state has initialized. `CoreContext`, `TaskMeta`, and
`TaskRegisters` describe this contract. The existing `resourceTasks` bridge
remains supported for bindings generated before core helpers moved into the
runtime.

### Component state

`intrinsics.component` implements all helpers from bindgen's `component.rs`.
`instanceFlags` contains the live canonical ABI `may_leave` globals. `asyncState`
maps component indices to `ComponentAsyncState` instances; `getOrCreateAsyncState`
returns the same instance for each index. `storeTrap` and `storeAsyncState` hold
the first trap and shared deadlock/wake-source accounting. These objects belong
to one runtime instance and are shared with the generated code. Providers that
delegate default methods must retain these state objects.

`ComponentAsyncState` manages backpressure, FIFO admission, task-owned execution
locks, and suspended tasks. Its handle table uses the resource namespace's shared
index allocator. Synchronous release callbacks run before lock handoff, and each
scheduler tick resumes at most one task, preserving JSPI task-register ordering.
Backpressure waiters resolve when the counter reaches zero and remove their
handlers. `ComponentTask`, `SuspendedTask`, and `AdmissionTicket` describe the
structural scheduler contracts while task implementations remain inline.

`guardMayLeave` and `guardTrap` preserve the wrapped function's receiver and
return value. Trap recording uses the selected `WebAssembly.RuntimeError` and
the core namespace's current-task register. Ordinary traps mark the affected
component; deadlock detection traps every component in the store and releases
queued admission and lock waiters. `trackHostOperation` accounts for pending
host promises and forwards their disposal methods, allowing deadlock checks to
distinguish blocked guest tasks from work that can still wake externally.

Generated bindings pass `options.componentTrapMessages` for the compiler's
engine-trap normalization and cannot-enter message. Direct users can supply
the same metadata; without it, engine messages remain unchanged and the default
cannot-enter message is used. `ComponentAsyncState.createWaitable` uses the
store's `intrinsics.waitable.Waitable` constructor. Older API-v1 bindings may
supply `options.componentContext.createWaitable`; that factory still takes
precedence to preserve their inline constructor identity. It is never called
during runtime creation. `ComponentContext`, `ComponentWaitable`, and
`ComponentTrapMessages` describe these contracts. Existing `coreContext` and
`resourceTasks` callbacks remain supported for earlier API-v1 bindings.

### Waitables

`intrinsics.waitable` implements all eight helpers from bindgen's `p3/waitable.rs`.
`Waitable` and `WaitableSet` are raw constructors shared throughout a runtime
instance. Providers that delegate default operations must retain these constructors
and the component namespace's handle tables so membership checks use the same
class identity. Set handles share the component's resource index allocator.

Waitables consume pending events once and reset their completion promise after
consumption. Joining moves a waitable from its previous set; joining `null`
removes it. Empty sets can be dropped only when no tasks are waiting on them.
Ready waits return synchronously. A built-in wait with `syncOnly` returns `-1`
when it would suspend; other waits can return a promise. Built-in waits and polls
do not deliver cancellation; cancellable callback waits retain task cancellation
delivery. `Waitable`, `WaitableSet`, and `WaitableTask` describe these contracts.

Generated bindings supply lazy `options.waitableContext` callbacks for current-task
lookup and storing event payloads in guest memory. They are called only when a
wait, poll, or drop needs them, after generated task state initializes.
`WaitableContext` and `WaitableStoreEventOptions` describe this bridge. Creating
waitables or sets, joining them, and calling `removeWaitableSet` need no task callbacks.
The legacy standalone `Waitable.waitForPendingEvent` hook accepts a scheduler
with `waitUntil`; generated bindings do not use that hook.

### Conversions

`intrinsics.conversion` implements all helpers from bindgen's `conversion.rs`:
numeric coercion and validation, integer/float bitcasts, character conversion,
string/result formatting, and 64-bit word splitting/merging. The exported
`ConversionIntrinsics` interface describes their arguments and results.

`options.strict` selects the same numeric checks as inline generation.
The 8/16/32-bit integer conversions validate before coercion; 64-bit conversions
coerce with `BigInt` before checking range. Without strict mode, integer values
wrap to their target widths. Bitcast scratch arrays are private to each runtime
instance. Conversion errors retain the inline implementation's JavaScript error
types and messages.

### JavaScript helpers

`intrinsics.jsHelper.emptyFunc` ignores its arguments and returns `undefined`.
`intrinsics.jsHelper.dataView(memory)` caches a `DataView` for the most recently
used memory buffer. Each runtime owns its cache; memory growth or switching
buffers refreshes the view. Both ordinary and shared memory buffers are supported.
The `JsHelperIntrinsics` type describes these helpers.

### Strings

`intrinsics.string` implements all helpers from bindgen's `string.rs`.
`utf8Decoder` and `utf16Decoder` expose `decode`, reject malformed input, and
preserve a leading U+FEFF. `utf8Encoder` exposes `encode` and `encodeInto`.
Each runtime owns its codec objects; alternative providers can supply objects
implementing the exported `StringDecoder` and `StringEncoder` interfaces.

`utf8Encode` and `utf16Encode` allocate and write strings into guest memory,
replacing unpaired host surrogates with U+FFFD. Their `Async` variants await
the supplied allocator before accessing memory. UTF-8 uses a single exact-size
allocation; its empty-string result is `{ ptr: 1, len: 0 }` without allocating.
UTF-16 lengths count code units, UTF-8 lengths count bytes, and non-sentinel
results also report codepoint counts. `StringAllocation`, `StringRealloc`, and
`AsyncStringRealloc` describe this contract.

`utf16ValidatingCopy` copies valid UTF-16 code units and reports whether they
all fit in Latin-1. `validateGuestChar` and `validateHostChar` retain the inline
character conversion behavior, including returning the first host codepoint.

### WebIDL

`intrinsics.webidl.globalThisIdlProxy()` returns the WebIDL adapter over the
host's `globalThis`, cached per runtime instance. It preserves bindgen's existing
accessor and setter conventions, HTML/DOM name normalization, method receivers,
and proxy argument unwrapping. `WebIdlIntrinsics` describes the provider method;
the returned object's properties depend on the host's available Web APIs.

### Resource tables

`intrinsics.resource` implements all helpers from bindgen's `resource.rs`.
`tableCreateOwn`, `tableCreateBorrow`, `tableRemove`, and `tableEnsureBorrowDrop`
manage ownership and borrow lifetimes. `transferOwn`, `transferBorrow`, and
`transferBorrowValidLifting` move resources between tables, retaining the inline
implementation's handling of reps returned to their defining table.
`callDestructor` runs a destructor in a fresh synchronous task and restores the
enclosing task's context on success or failure.

`resource.tableGet(table, handle)` reads an array-like table without modifying
it and returns `{ rep, scope, own }`. The table layout is Jco's JavaScript
representation of a Canonical ABI resource table and is part of the JavaScript
CM runtime API:

- Slots 0 and 1 form a sentinel, and resource handles start at 1. Handle indices
  are allocated from a space shared by every handle kind of a component instance,
  so a table may have holes for indices that belong to other kinds.
- Slot `handle << 1` contains the scope. Bit 30 marks a freed entry.
- Slot `(handle << 1) + 1` contains the representation, with bit 30 indicating
  ownership. Clear that bit to obtain `rep`. A freed entry stores zero.
- A slot past the end of the table, a decoded representation of zero or a freed
  entry causes `tableGet` to trap with `unknown handle index <handle>` using the selected
  `WebAssembly.RuntimeError` constructor.

`ResourceTable` describes the resizable array and its `_createdReps` set and
optional `_componentIdx`. `resource.tableFlag` exposes bit 30. All handle kinds
of a component share the allocator returned by `getHandleIndexSpace(componentIdx)`;
a table without a component index uses the table itself as its allocator key.
Freed indices are reused in LIFO order.

`resource.state` holds per-store handle tables, allocator maps, scope counters,
scope-to-task mappings, and borrow lists. Generated code accesses mutable fields
directly, so replacing a borrow list or incrementing a counter remains visible
to both runtime methods and inline task helpers. Providers that delegate methods
to this implementation must preserve its state object. `ResourceState`,
`HandleIndexSpace`, and `ResourceBorrowTask` describe these shared structures.

During this migration, generated bindings pass lazy callbacks through
`options.resourceTasks` when resource transfers or destructors need task helpers
that remain inline. `getCurrentTask` returns the destination component's active
borrow task; `createTask` and `withTask` supply the destructor's task lifecycle
and scoped task register. Providers must defer these callbacks until a resource
operation runs: generated task state initializes after runtime creation.
`ResourceTaskContext` and `ResourceDestructorTask` describe this bridge.
Direct users can allocate and transfer resources without a task context;
calling a destructor requires `createTask` and `withTask`.

Incompatible changes to this table encoding or these method contracts require
a new JavaScript CM runtime API version, independently of the npm package version.
